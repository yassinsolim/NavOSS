Internal beta policy · Effective November 12, 2026

Privacy without an account

NavOSS is operated by Yassin Soliman as an individual developer in Alberta, Canada. It is an account-free navigation technical beta with Calgary and Kelowna search and routing plus selected official regional overlays.

This policy is ready for internal TestFlight. External testing remains blocked until a direct privacy and support email has been activated and tested.
Community features are not switched on. Community traffic sharing and shared community road reports are described below because the NavOSS server and the app code support them, but neither is switched on in the deployed service, and no released version of the app (the latest is 0.1.0 (70)) sends traffic observations or shares road reports. This policy will say so until that changes.

Location and active navigation

When you grant When in Use location permission, precise location shows your position, chooses a route origin, matches progress to an active route, detects rerouting and arrival, and checks whether an official safety camera is ahead.

After you start turn-by-turn navigation, location updates continue while the phone is locked, another app is visible, or CarPlay is connected. iOS displays its background location indicator. NavOSS does not request Always location. Updates stop on End or confirmed arrival. The current active route, and the last position along it that NavOSS confirmed, are stored transiently on the phone so that a relaunch can resume the trip. That position is kept as distances along the route, with the time and speed of the GPS fix that confirmed it, not as coordinates; with the route, it still identifies where you were. Both are erased when navigation ends or arrival is confirmed, or at the first launch 12 hours or more later; NavOSS does not maintain a trip-history database. If you switch on traffic sharing, positions along through roads are also sent during navigation as described under Community traffic sharing; it is off unless you turn it on, and it is not switched on in the deployed service.

Search and routing

Search text and, when available, a search origin rounded to three decimal places, or roughly 100-meter granularity, are sent in an encrypted request body to the NavOSS API. Route requests send precise origin and destination coordinates. An automatic reroute sends the latest route origin and destination. Search uses self-hosted Alberta and British Columbia OpenStreetMap data plus a local mirror of public Calgary business and parcel-address data used only for Calgary searches. Current production uses Valhalla on the operator-controlled server in Alberta. A future licensed live-traffic deployment may forward route endpoints and preferences to Mapbox Directions; that mode remains disabled until its commercial vehicle-use license and release gates are complete.

These values are processed in memory for the response and then discarded. They are not written to a NavOSS database, access log, or backup. Active route matching and camera eligibility run on the phone.

Tapping a named map place sends that public place name and map coordinate to the same NavOSS API to find the nearest matching OpenStreetMap record. When available, the response may include a public address, category, opening hours, business phone number, official website, and wheelchair-access tag. The request is processed in memory and discarded like typed search. NavOSS does not fetch Google review content in this lookup.

In a build where Google Places details are explicitly enabled, opening a point-of-interest sheet also sends that selected public name and coordinate directly to Google Places. Google's Places UI Kit chooses the place and renders available photos, the star rating and rating count, review text, and required Google attribution inside its own visually separated component. NavOSS reads only the returned display name and coordinate to reject a mismatched place; it does not read, persist, combine, or send the photo, rating, count, or review values to its server. A build without the restricted Google key makes no place-details request and shows that Google photos, ratings, and reviews are unavailable.

Before an enabled phone opens Google's component, it asks the NavOSS API to reserve one anonymous monthly query grant. That request contains no place name, coordinate, account, device identifier, or search text. NavOSS stores only the UTC month, an aggregate used count, and its last update time. The server denies grants after 8,000 in a month, below Google's current 10,000-event no-charge allowance, and fails closed if the counter is unavailable.

An enabled build links GooglePlacesSwift 10.15.0 and its underlying Google Places SDK. The SDK's embedded Apple privacy manifest declares Google collection of precise and coarse location for analytics and app functionality; device ID linked to identity for analytics and app functionality; other data linked to identity for analytics; and unlinked performance data, product interaction, and search history for analytics. It declares no tracking. These are Google-controlled SDK declarations beyond the place details NavOSS displays, and enabled-build App Privacy answers must include them.

Map style, navigation orientation, tilt, map-content visibility, safety-camera marker visibility, and route-color choices are stored only inside the app on the device. NavOSS does not receive these settings or use them for analytics. Hiding camera markers does not disable active-navigation safety warnings.

Sharing and external place actions

Place sharing and Share ETA use Apple's system share sheet. Place share text contains a public place name, displayed address or category, and OpenStreetMap link. ETA share text contains the chosen destination name, arrival estimate, remaining time, and remaining distance. It does not contain the current coordinate, route geometry, live tracking, or automatic updates. NavOSS does not read Contacts or request Contacts permission; it does not receive or store the recent recipients Apple may suggest.

Call and website actions open an external system app only after the user chooses them. More reviews on Google Maps is a separate external action and sends the selected public place name and coordinate to Google only when chosen. NavOSS does not scrape or cache review text. In a Google-enabled build, the place-details request described above can occur when a point-of-interest sheet opens; the external Google Maps search still occurs only after the user chooses it.

Contribute sends private beta feedback to NavOSS without an account, device identifier, or precise coordinate. To limit abuse, the API keeps a salted, process-local fingerprint of the source network address for up to one hour; it is not logged or stored in PostgreSQL. Accepted submissions contain a fixed type, description, optional place or road label, timestamps, random identifiers, and review status. They are not public and are scheduled for deletion from the live database after 90 days; bounded backups may retain a deleted row for up to 14 additional days. Failed submissions remain only on the device for retry, up to 25 attempts.

NavOSS does not automatically transmit raw feedback descriptions to an AI provider. Operator policy requires reviewing raw text outside an AI conversation. After manually removing names, private addresses, contact details, exact personal trips, credentials, and unnecessary timestamps, the operator may create a separate deidentified engineering summary stored in an ignored local workspace artifact. Only when the operator explicitly invokes AI-assisted triage is that summary transmitted to the configured coding-assistant provider under its terms, to group reports, draft issues, or help implement a human-approved item. The summary contains no account or contributor identifier.

Community traffic sharing (opt-in)

Not switched on. The NavOSS server supports traffic sharing, but it is not switched on in the deployed service, and no released version of the app (the latest is 0.1.0 (70)) sends driving observations. This section describes the app version that adds the Share traffic speeds switch and what the server does with what it would receive. Statements about what the app does are requirements for that version; no released app has been checked against them yet.

NavOSS can build live traffic from the driving speeds of people who choose to share them. Traffic sharing is off by default.

What is sent. While sharing is on and turn-by-turn navigation is active, the app sends short batches of your driving positions to the NavOSS API. A batch is a list of positions, each with the number of seconds since the batch's first position, plus the time the batch started rounded down to the minute, plus an upload credential (described below). A batch covers about one minute of driving and never more than five. It contains no account, no name, no advertising identifier, no trip or sequence identifier, no destination and no planned route. It does contain a short stretch of the path you actually drove. Batches from one trip carry the same upload credential, come from the same network address, and continue where the previous one stopped, so the server and Cloudflare could link them while they are being delivered. NavOSS does not record that link.

Upload credentials and abuse resistance. To make made-up traffic harder, the server accepts batches only with an upload credential, and issues one only to an installation of the app that has registered an Apple App Attest key for NavOSS and signs a fresh request with it. For that key the server stores a keyed hash of the key's identifier, the public key in encrypted form, a counter, whether Apple attested it, and the times it was registered and last used. A periodic cleanup deletes a key after 90 days without use; it is best effort, so a key can remain somewhat longer if a cleanup run fails. A key registered less than a day earlier gets no credential yet. The credential is valid for two hours. The server keeps no record of which installation a credential was issued to, and nothing it stores about traffic refers to an installation or a credential, but asking for a credential does update the key's counter and “last used” time.

App Attest shows that a request was signed by a genuine copy of the app on an Apple device. It does not show that the device was driving, and one iPhone can register several keys. A credential is a bearer token: whoever holds it can upload with it until it expires, from any device. A test setting makes the server accept software keys instead; the committed production configuration leaves it off, and the enablement checklist requires that.

When it is sent. Only during active turn-by-turn navigation, including while the phone is locked or CarPlay is connected, about once a minute. Nothing is sent while you browse the map, search, preview a route, or drive without navigation, and nothing is sent when sharing is off. The server refuses a batch whose first position is more than 10 minutes old when it arrives.

What is left out. The app is required not to record the first 400 metres or the last 400 metres of a trip, or anything within 400 metres of your destination or a stop on the way, and to hold back the most recent 400 metres so that a trip you end early never sends its final stretch. The server cannot check this, because it is never told where a trip starts or ends. What the server itself does is discard the first and last 100 metres of every batch it receives and use only motorways, trunk roads, primary roads and secondary roads. Of those, it uses only stretches at least 20 metres long that the routing software's map marks as open to cars and as neither private or destination-only access nor a dead end or the road into or out of an area with no other exit. That map check reaches only as far as the routing software looks: a large area with a single exit, such as a valley with its own road network, can still be used. Positions on other roads (tertiary and residential streets, service roads, driveways, tracks, and parking areas) may still be uploaded and matched to the map in memory, but nothing is kept from them.

What the server does. The server matches a batch to roads in memory and works out, for each qualifying stretch between two junctions, which part of it the batch drove (as distances along the stretch), how far you moved there and how long you spent there, including time stopped. A stretch is often longer than one batch covers, so the parts you drive of one stretch in successive batches are joined; once they cover 300 metres of it, or half of it if it is shorter, they become your one speed for that stretch (distance over time). The speed is measured on the part driven and shown for the whole stretch. It holds these figures in memory and discards the batch. The NavOSS API does not write your positions, the batch, or its timing to its database, a backup, or its log. To match a batch to roads and check the map the API uses routing software (Valhalla) that it requires to be at a local network address; on the production stack that is a container on the same NavOSS-controlled machine in Alberta. The address check by itself does not prove where the software runs or who operates it, and NavOSS will confirm the production deployment before switching publication on. Batches are not forwarded to another routing provider. The map check sends the routing software only points on the map's own roads, never your positions. Like every request to NavOSS, a batch is delivered through Cloudflare, which sees it in transit. NavOSS has not yet verified that the routing software, the reverse proxy's error handling, system swap, or crash dumps on the production machine never write any part of a batch, and will not switch publication on until it has.

What is kept, and for how long.

  • Before publication, in memory only. For each stretch of road, the server's memory holds one speed per contributor (or, until enough of the stretch is covered, which parts of it the contributor has driven, how far and for how long), the five-minute period in which it arrived, when the batch's driving began, and a scrambled marker that tells contributors apart. The marker is derived from your App Attest installation and that one stretch of road using a secret that exists only in the running server's memory. Markers for two different roads are unrelated, so they cannot be matched to each other by comparing them; your marker for one stretch stays the same across five-minute periods and credentials until the server restarts. For an installation registered in the last seven days, the memory also holds a scrambled marker of the network the batch came from, so that several new keys on one network count once. This is dropped after at most 20 minutes and is lost whenever the server restarts. It is never written to the database.
  • After publication, in the database. Once at least three installations have driven the same stretch, the server stores one typical speed for it, rounded to 5 km/h, the public OpenStreetMap shape of that stretch, and the five-minute boundary at which it was published. It is never shown after 15 minutes. It is deleted at that point by the server's next successful database update, which is normally at that moment and otherwise at a later five-minute boundary; it is erased whenever the server starts (including when the feature is switched off, in which case the server retries until the erasure succeeds); and it is excluded from database backups. Nothing deletes it while the server is stopped.
  • Abuse limits, in memory only. The server keeps salted fingerprints of the source network and of the contributor, with request times, for up to 11 minutes after the last request.
  • Operator counters. Every 15 minutes the server logs running totals (batches, credentials, stretches published, failures). They contain no road, position, address or installation and are kept as long as other operational logs.

Everything derived from a batch leaves memory within 20 minutes of its arrival and is no longer shown within 35 minutes; physical deletion from the database can be later, as described above. These periods, the minimum of three contributors, and the road rules are fixed in the server's code and cannot be weakened by configuration.

What other drivers see. A stretch of road is coloured, and can affect an estimated arrival time, only after at least three different App Attest installations have each driven at least 300 metres (or half) of that same stretch, in batches whose driving began within the 15 minutes before a five-minute boundary, and only from that boundary. It stays shown for at most 15 minutes, so what other drivers see rests on driving at most 30 minutes old. Three installations are three keys, not necessarily three people. A stretch driven by one or two contributors is never shown and never stored. Other drivers see, for each published stretch, its shape, a congestion colour, a typical speed rounded to 5 km/h, the road's normal speed, and the five-minute boundary at which it was published. They never see a vehicle, a trip, a count of contributors, or who contributed. With few contributors, most roads will show no traffic at all.

What NavOSS cannot rule out. This is data minimisation with a threshold, not anonymity.

  • Three installations are not necessarily three unrelated people. They can be one household, or one person who has registered several keys and kept them for a week or used several networks.
  • On a quiet road, the fact that a stretch was driven by at least three contributors shortly before a given five-minute boundary becomes visible to anyone watching the map, and the small group who drive there may be guessable.
  • If two of the three contributors on a stretch cooperate, they can infer that a third person drove it in that window, roughly how fast, and at a junction which way they went.
  • Someone with access to the running server's memory, together with its database, could work out which installation contributed to a stretch that is still waiting for publication.
  • Cloudflare and the NavOSS server necessarily see each upload and its network address while it is being delivered, as they do for every request.
  • A home on a secondary or larger through road is on a road the server uses. Only the trimming the app performs and the three-contributor rule protect it.

How to turn it off. Turn off Share traffic speeds in the app's About and Privacy screen. Uploads are required to stop immediately and anything not yet sent to be discarded. Ending navigation or removing the app has the same effect. What was contributed stops being shown within 35 minutes and is deleted as described above. Nothing about traffic is stored with an account, an installation, or a trip identifier, so there is no per-person traffic record to look up or delete. You can see traffic from other drivers without sharing your own.

Community road reports

Not switched on. Sharing road reports is not switched on in the deployed NavOSS service, and no released version of the app (the latest is 0.1.0 (70)) contains the sharing client: released builds keep only the private drafts described at the end of this section. The paragraphs below describe the app version that adds Share road reports.

NavOSS can share structured road reports between drivers. The NavOSS server decides whether sharing is on (features.communityReports); it is off until the operator enables it. While it is off, or on a device that cannot use Apple App Attest, the app keeps the private drafts described at the end of this section and sends nothing.

What a report sends. Reports are shared only after you turn on Share road reports (off by default; until then every report stays a private draft). Within 400 m of your saved Home or Work, or of the current trip's start, destination or stops, a report stays private unless you explicitly confirm sharing it. When sharing is on and you choose a report type, the app sends one of eight fixed types (crash, road closed, slow traffic, construction, pothole, object on road, other hazard, stopped vehicle), your current precise coordinate, your direction of travel in whole degrees when known, and an App Attest signature with its key identifier. It contains no free text, photo, name, account, destination, or route. The server stores the precise coordinate and a copy snapped to a grid of about 55 m by 35 m. Other drivers receive only the snapped position, the type, the report and expiry times rounded to five minutes, and a confirmation count; never who reported it. A report expires after two hours; confirmations can extend it to at most 12 hours after it was made, and “not there” answers shorten or end it. No report changes a route.

Reading reports. The app asks the server for reports in the area you are viewing or, during guidance, in a box around the route ahead (at most half a degree each way). These requests carry no identity, and the app keeps the answers in memory only. The CarPlay map shows the same reports. During guidance the app can show, and if Spoken road reports is on and the guidance sound allows alerts, speak a short alert for a report ahead.

Still there? After you pass a report, and never near a turn, the app may ask whether it is still there. Still there or Not there sends that answer with your current coordinate, which the server uses only to check that you are within 1.5 km of the report and then discards. Letting the question disappear sends nothing. The app does not ask about reports you made during the same app session.

Identity and deletion. The first report registers an App Attest key for this installation. The phone stores only the key's identifier, in the iOS Keychain on this device; the key itself stays in the iPhone's Secure Enclave. The server stores the key as described under Community traffic sharing, plus, for 24 hours, the position of the installation's latest report or answer rounded to about 1 km, to reject impossible travel. You can withdraw a report you made in the same app session. Reset community identity deletes the installation from the server with all its reports and answers, and forgets the key on the phone; a later report registers a new key that is not linked to the old one. Development builds running in the iOS Simulator can use a software key that only a test server accepts; release builds cannot.

Private drafts. When sharing is off or unavailable, the report button stores up to 25 structured road-report drafts on the device. Each draft contains one of the eight fixed report types, the current precise coordinate, its creation time, and a two-hour expiry time. It contains no free text, photo, account, or public user name. Drafts are not sent to NavOSS or a third party and are not shown to other drivers. Expired drafts are discarded when the local list is next read or written, and removing the app removes all remaining drafts.

No advertising or cross-app tracking

The default Google-disabled build has no account system, ads, analytics SDK, advertising identifier, data broker integration, or cross-app tracking. It does not use an advertising identifier or create a persistent user or device identifier, except that a phone which turns on traffic sharing or community road reports registers an App Attest key, described under Community traffic sharing and Community road reports, which the server keeps until 90 days after its last use. Location is not used by NavOSS for advertising or user profiling. A separately enabled Google place-details build links the Google Places SDK and is subject to the SDK declarations above; NavOSS does not receive or operate that Google analytics data.

Map and camera data

The phone requests map styles, tiles, fonts, and sprites directly from OpenFreeMap. The requested resources can indicate the viewed map area. OpenFreeMap says regular logs omit IP addresses, while it may retain incident IP logs for up to 30 days. Regional data can include Calgary and Toronto enforcement cameras, Ontario 511 and DriveBC road events, DriveBC ordinary traffic webcams, and fixed public Kelowna RCMP facilities. The phone selects a region locally and sends only the region identifier for those requests. DriveBC webcams are not enforcement cameras, and RCMP facilities are not live police locations.

Providers and retention

Cloudflare provides DNS, TLS, traffic delivery, and the outbound tunnel. It processes client IP and network/request metadata on its global network under its policy. NavOSS does not enable raw Cloudflare request-log export. Map delivery uses OpenFreeMap; TestFlight feedback, the user-invoked system share sheet and App Attest, which the phone uses to create the key that signs community road reports and obtains traffic-upload credentials, use Apple; and user-initiated support may use GitHub. Optional Google-rendered place details and a user-selected external reviews action use Google under Google's policy. Optional licensed live-traffic routing may use Mapbox and send route endpoints, preferences, and request network metadata; it is disabled in current production.

NavOSS keeps operational, SSH, and firewall logs for no more than seven days. Routine HTTP access logging is disabled. Logs exclude request bodies, search text, and route coordinates. The report database has 14-day backups that may contain accepted private beta feedback; route and search requests never enter those backups, and reproducible public search-index tables are excluded. The Google query safety counter stores only the UTC month, aggregate used count, and last update time.

NavOSS's operational logs exclude HTTP request and response bodies, search text, route coordinates, shared traffic positions, and normal HTTP access events. NavOSS has not yet verified that the routing software and the reverse proxy never log request content or client addresses when a request fails; traffic publication stays off until it has. When traffic sharing is enabled on the server, a periodic summary records only counts of batches, credentials, and road stretches, with no road, position, address, or installation.

Your choices and deletion

You can deny or revoke location permission in iOS Settings and can stop an active trip with End navigation. Search and map browsing may remain available, while current-position routing and active guidance will be limited.

NavOSS stores up to 12 recent destinations and 20 places you save, including their names, labels, and coordinates, only on the device for phone and CarPlay shortcuts. Use Clear saved and recent destinations in About and Privacy to erase both local lists. Pending contribution retries can be deleted individually on Contribute. Accepted feedback expires automatically after 90 days; its displayed random reference can be provided to support for earlier deletion. Road-report private drafts expire after two hours. Reset community identity deletes this installation's shared road reports and answers from the server, as described under Community road reports. Removing the app removes the remaining local records.

Traffic sharing is optional and off by default; turn Share traffic speeds off in About and Privacy to stop it, as described under Community traffic sharing.

Sharing and the external reviews link are optional. Dismissing the system share sheet sends nothing to a recipient. In a Google-enabled build, opening a POI sheet can send its public coordinate for Google-rendered photos, ratings, and reviews; not choosing the external link sends no Google Maps review search. NavOSS does not ask for Contacts access.

Because NavOSS has no account and does not retain server-side search, route, or trip records, it normally has no server history to export or delete. Published traffic speeds are stored without an account, installation, or trip identifier and only as short-lived per-road values once at least three installations have driven a stretch (their speeds are combined into a median; they are not checked for agreement). Speeds waiting for publication are held only in memory, under markers the running server could recompute from an installation. The residual ways a contribution could still be inferred are listed under Community traffic sharing above. A rights request may identify a support message or recent security event, but NavOSS may be unable to associate a transient, IP-only request with a person. Requests about provider-controlled data may also need to be directed to that provider.

Security and international processing

App-to-API traffic uses HTTPS through Cloudflare. The Alberta origin uses an outbound tunnel rather than a public inbound port, key-only SSH, a default-deny firewall, least-privilege containers, security updates, bounded logs, and read-only filesystems where practical. No security measure can guarantee absolute protection.

The NavOSS origin is in Alberta. Cloudflare, OpenFreeMap, Apple, Google when place details are enabled or the external reviews link is chosen, GitHub, and a user-selected share destination may process data outside Canada as described in their policies.

Children and changes

NavOSS is a general-audience navigation utility and is not directed to children. It does not create profiles or knowingly maintain children's personal information. A parent or guardian should supervise a minor's use of navigation and support channels.

Material changes will appear here with a revised effective date. During beta testing, material data-use changes will also be identified in TestFlight release notes before the changed feature is tested.

Contact

Use the repository's public issue tracker only for non-sensitive questions. Use private vulnerability reporting for a security issue or sensitive privacy request. Internal testers may also use TestFlight feedback. Never publish a private address or precise trip history. The planned address navoss@yassin.app is not presented as active until delivery and reply handling are tested.
